# AX브릿지 10분 검토 가이드

목표는 중개 운영 흐름과 역할별 화면이 업무에 맞는지 확인하는 것입니다. 아래 내용은 **사용자가 수행할 점검 절차와 기대 동작**이며, 브라우저 검수 또는 테스트 통과 보고서가 아닙니다.

제작 환경의 로컬 주소 브라우저 차단과 Chromium 소켓 권한 제한 때문에 실제 브라우저 스크린샷·모바일 시각 검수는 완료하지 못했습니다. 자동 렌더 검증과 실제 화면 점검은 구분해서 기록하세요.

## 시작 전

- Node.js 24 이상에서 `npm start`를 실행하고 같은 컴퓨터/VM의 `http://127.0.0.1:4318`을 엽니다.
- 실제 개인정보 대신 가상 회사명·담당자·요구사항을 사용합니다.
- 기존 입력이 있다면 관리자 **데이터 관리 → JSON 백업 받기**부터 진행합니다.
- 초기 상태가 필요할 때만 **시연 데이터로 초기화**를 사용합니다. 현재 입력 내용이 전체 교체됩니다.
- 샘플 일정은 처음 생성한 날짜를 기준으로 만들어지므로 아래 특정 날짜 대신 프로젝트명을 기준으로 찾습니다.

## 0–1분 · 운영 개요

1. 관리자 대시보드에서 진행 중 의뢰, 희망 예산 합계, 접수 견적, 검수 대기를 확인합니다.
2. 샘플 고객·금액이 가상임을 표시하는 문구와 로컬/로그인 미설정 안내를 확인합니다.
3. **프로젝트**에서 보드/목록을 바꾸고 서비스 유형·단계·검색 필터를 사용합니다.

확인할 점: 고객 희망 예산을 매출로 오해하지 않는가? 오늘 할 일과 검수 대기를 바로 찾을 수 있는가?

## 1–3분 · 고객 의뢰와 영업 CRM

1. 프로젝트를 하나 만듭니다. 이름은 `가상 검토 의뢰`, 고객사는 `가상 테스트컴퍼니`처럼 입력합니다.
2. AX 구축을 선택하고 문제·요구사항·예산·희망 완료일·가상 담당자를 입력합니다.
3. 영업담당자를 배정하고 저장합니다.
4. **영업 CRM**에서 해당 고객을 찾아 통화 또는 미팅 기록과 다음 할 일을 추가합니다.
5. 상단 관리자/영업 시연 선택을 바꾸고 배정된 의뢰만 나타나는지 확인한 뒤 관리자로 돌아옵니다.

확인할 점: 고객사·담당자·담당 영업자·최근 상담·다음 행동이 한 흐름으로 연결되는가? 영업담당자 등록은 직원 계정 생성이 아니라 내부 명부임을 이해할 수 있는가?

## 3–4분 · 비교와 내부 선택

1. **견적 비교**에서 `매장 마케팅 운영 정리`를 선택합니다.
2. 공급사별 금액뿐 아니라 포함 범위·제외 비용·기간·운영 지원·유효일을 비교합니다.
3. 수신한 견적 하나를 선택합니다. 선택 표시는 내부 결정 기록이며 계약 체결이 아닙니다.
4. 프로젝트 단계에서 진행으로 변경합니다.
5. 별도로 만든 새 의뢰는 견적 선택 없이 진행으로 변경해 보고, 거부 메시지가 나오는지 확인합니다.

확인할 점: 요청 중인 견적을 확정 견적으로 오해하지 않는가? 실제 계약·외부 발송이 일어나지 않는다는 설명이 보이는가?

## 4–5분 · 교육과 인프라 전용 정보

1. `실무자 AI 활용 교육`의 의뢰와 견적에서 교육 대상·인원·목표·시간, 커리큘럼·실습·강사를 확인합니다.
2. AI 교육이 외부 교육업체 중개라는 맥락과 후보 업체의 미확정 관계를 확인합니다.
3. `사내 AI 테스트 장비 검토`의 의뢰와 견적에서 도입 목적·기존 환경·설치 장소, 장비 사양·수량·설치비·납기·보증을 확인합니다.

확인할 점: 일반 AX 구축과 교육·인프라의 비교 기준이 구분되는가? 인프라 설치비를 총액에 다시 더하지 않도록 이해할 수 있는가?

## 5–7분 · 공급사 제출, 수요기업 검수, 완료 가드

1. 공급기업 포털에서 `가상 데이터스튜디오`와 연결된 `영업 리포트 자동화`를 찾습니다.
2. 제출할 결과물의 위치/설명과 견적 정보를 검토합니다. 마일스톤은 내부 선택된 견적의 공급사만 볼 수 있습니다. 제출은 파일 업로드가 아니라 텍스트 기반 기록이며 이미 승인된 결과물은 공급사가 수정할 수 없습니다.
3. 수요기업 포털에서 같은 의뢰를 선택하고, 제출된 마일스톤에 수정 요청 또는 검수 승인을 남깁니다. 아직 제출하지 않은 마일스톤의 승인/수정 요청 상태 변경은 거부되어야 합니다.
4. 관리자로 돌아와 미승인 마일스톤이 남은 상태에서 프로젝트를 완료하려고 합니다. 완료를 막는 안내가 나와야 합니다.
5. 모든 마일스톤을 검수 승인한 뒤 프로젝트 완료를 별도로 선택합니다. 마지막 승인만으로 자동 완료되지는 않아야 합니다.

주의: 완료된 프로젝트의 검수를 다시 열 때는 프로젝트를 먼저 미완료 단계로 변경하세요. 완료 상태에는 모든 마일스톤이 승인되어야 한다는 저장 규칙이 계속 적용됩니다.

확인할 점: 수요기업은 자기 의뢰를, 공급기업은 연결된 자기 견적을 중심으로 보는가? 선택되지 않은 공급사에 다른 공급사의 납품·검수 기록을 보여주지 않는가? 경쟁 견적과 관리자 전용 메모를 노출하지 않는 응답을 사용하는가? 역할 선택 자체는 누구나 바꿀 수 있는 데모이므로 실제 보안 검증으로 간주하면 안 됩니다.

## 7–8분 · 지원사업과 투자 검토

1. 관리자 **지원사업**에서 공식 출처·사업 연도·접수 기간·대상 요건·혜택·자부담·확인 메모를 읽습니다.
2. 정책·예산 발표와 개별 모집 공고를 구분합니다. 가상/미검증 레코드에 대해서는 실제 접수 중이라고 판단하지 않습니다.
   - 공식 자료 스냅샷의 확인일은 2026-10-05 KST입니다. 접수기간 내였던 충북 제조 AI·스마트서비스 A/S도 대상 제한과 현재 날짜를 다시 확인합니다.
   - 2027 스마트공장 자료는 주관기관 모집, 2026/2027 예산자료는 정책 참고입니다. 일반기업 신청 안내로 오해하지 않아야 합니다.
3. 지원사업을 가상 의뢰와 연결하고 다음 행동과 기한을 저장합니다. `신청 완료`는 실제 제출 없이 바뀌는 내부 기록임을 확인합니다.
4. **투자 검토**에서 직접 투자 검토와 투자자 연결을 구분하고 상태·다음 행동을 변경합니다.
5. 영업직원·수요기업·공급기업 관점에 투자 데이터가 제공되지 않는지 확인합니다.

확인할 점: 외부 기관 신청, 투자자 연락, 금융거래가 자동 실행되는 화면으로 오해할 여지가 없는가?

## 8–9분 · 검토용 가입

1. **검토용 가입**을 열고 수요기업 또는 공급기업을 선택합니다.
2. 가상 회사명과 가상 담당자 정보로 등록합니다. 이메일이 필요하면 실제 수신함 대신 `demo@example.test` 같은 테스트 주소를 사용합니다.
3. 수요기업은 로컬 의뢰, 공급기업은 후보 공급사 기록이 생성되는지 확인합니다.
4. 관리자 가입, 비밀번호 입력 또는 이메일 인증이 있다고 오해하게 만드는 표현이 없는지 확인합니다.

새 공급사 가입만으로 프로젝트가 자동 배정되지는 않습니다. 관리자에서 해당 공급사와 의뢰를 견적 관계로 연결해야 공급기업 포털에 연결 의뢰가 생깁니다.

## 9–10분 · 저장과 복원

1. 관리자 **데이터 관리**에서 JSON 백업을 받습니다.
2. 가상 메모를 하나 변경하고 새로고침하여 저장 여부를 확인합니다.
3. 서버를 정상 종료하고 같은 폴더에서 재실행해 기록이 유지되는지 확인합니다.
4. 백업 불러오기로 이전 JSON을 선택하고 전체 교체 안내를 읽은 뒤 복원합니다.
5. 영업활동·지원 신청·투자 검토까지 함께 이전 상태로 돌아오는지 확인합니다.

초기화·불러오기를 반복하기 전에 보관할 백업 파일명을 구분하세요. 자동 백업이 없으므로 최신 내용이 필요한 상태에서 오래된 파일로 교체하면 복원 가능한 최신 사본이 남아 있어야 합니다.

## 추가 점검 목록

시간을 더 들일 수 있다면 아래도 확인합니다.

- 필수값 누락, 잘못된 이메일·날짜·음수 금액, 종료일이 시작일보다 빠른 지원사업 저장 거부
- 선택한 견적·사용 중인 공급사·연결된 지원사업·배정된 영업자 삭제 거부
- 프로젝트 삭제 시 연결 기록도 삭제된다는 안내와 영향 범위
- 잘못된 JSON/참조가 깨진 백업 가져오기 실패 후 기존 데이터 유지
- 검색 결과 없음, 신규 가입 후 연결 의뢰 없음, 모든 할 일 완료 상태
- 저장 버튼 연속 클릭, 취소/닫기, Escape, 브라우저 뒤로/앞으로, 새로고침 후 상태
- 키보드 탐색·포커스, 폼 오류 안내, 작은 화면에서 가로 넘침과 텍스트 읽기
- `npm test`의 실제 종료 코드와 테스트 요약

## 검토 메모 양식

| 항목 | 기록 |
| --- | --- |
| 실행 환경 | 운영체제/VM, Node 버전, 브라우저·화면 크기 |
| 실제 실행한 점검 | 자동 테스트 / 화면 수동 점검 / API 확인 등을 구분 |
| 결과 | 통과·실패·미실행을 구분 |
| 재현 경로 | 화면 → 선택 항목 → 입력 → 실행한 버튼 |
| 기대/실제 동작 | 무엇이 달랐는지 |
| 후속 결정 | MVP에 필요한 수정 / 실서비스 후속 범위 |

실제 고객으로 검토 범위를 넓히거나 서버를 공개하기 전에는 인증·권한·개인정보·계약·업무 책임 검토가 먼저 필요합니다.
